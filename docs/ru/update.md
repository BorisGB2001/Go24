# Обновление go24

Новые версии выходят на GitHub: https://github.com/BorisGB2001/Go24/releases. У каждой есть номер `X.Y.Z` и список
изменений. Номер устроен так:

- **последняя цифра** (0.5.**3**) — исправления и небольшие доработки, обновлять можно смело;
- **средняя цифра** (0.**6**.0) — новые разделы и крупные изменения; перед обновлением прочитайте список изменений.

## Обновление по кнопке (основной путь)

**Настройки → Обновление** (администраторы) показывает установленную версию, последний выпуск на GitHub со списком
изменений и кнопки **Проверить**, **Обновить до X.Y.Z** и **Откатить на X.Y.Z**. go24 сам проверяет GitHub раз в
6 часов; новая версия видна на этой странице, уведомлением она не приходит.

**Обновить** делает всё то же, что ручные шаги ниже:

1. go24 скачивает из выпуска `go24-X.Y.Z.tar.gz` и подпись `go24-X.Y.Z.tar.gz.sig` и проверяет подпись (ed25519;
   открытый ключ встроен в go24, закрытый есть только у того, кто публикует выпуски). Архив с чужой или испорченной
   подписью и версия не новее установленной не ставятся.
2. Дальше работает служба `go24-updater`, каждый шаг виден на странице вживую:
   - ещё раз проверяет подпись (go24 она не доверяет);
   - делает копию всех баз в `deploy/backups/before-<старая версия>-<дата>.sql.gz` и сохраняет для отката текущие файлы,
     `deploy/.env` и образы go24;
   - раскладывает новые файлы поверх установки; `deploy/.env`, тему, свои языки, собранные настройки мессенджера и
     резервные копии не трогает;
   - дописывает в `deploy/.env` параметры, появившиеся в новом `deploy/.env.example` (пустые пароли и секреты
     генерирует), и перечисляет их в журнале;
   - если изменились шаблоны мессенджера — пересобирает его настройки (как `make matrix-config`);
   - `docker compose pull` и `up -d --build`: новые версии компонентов приходят с закреплёнными в выпуске тегами образов;
   - до 10 минут ждёт, пока `go24` и `go24-worker` станут healthy и ответит `/healthz`.
3. Если go24 не поднялся, прежняя версия возвращается сама: её файлы, настройки и образы, база — из копии; в статусе —
   **откат** и причина.
4. Администраторам приходит уведомление (и сообщение в мессенджер — по их настройкам): «обновлён до X.Y.Z» или
   «откат: причина».

Обновление с любой старой версии сразу на последнюю работает: миграции всех промежуточных версий применяются по порядку.

**Откатить** возвращает версию, сохранённую перед последним обновлением, вместе с её базой. Всё, что изменилось в go24
после того обновления, теряется — это крайняя мера.

У сборки для разработки (версия с суффиксом, например `0.6.0-dev`, или `GO24_UPDATE=off` в `deploy/.env`) кнопки нет:
её код не из выпусков GitHub, она обновляется через git.

## Ручное обновление (запасной путь)

Если кнопка недоступна (с сервера нет доступа к GitHub, `go24-updater` не работает).

### Схема

```
  1. копия  ──►  2. новый код  ──►  3. новые настройки?  ──►  4. перезапуск  ──►  5. проверка
  (2 мин)        (git checkout)     (обычно нет)               (make up)          (открыть go24)
```

База обновляется сама: при запуске go24 применяет новые миграции. Данные, файлы и настройки сохраняются.

### Шаги

Всё выполняется на сервере от пользователя `go24` в папке `/srv/go24`.

**1. Копия перед обновлением.** На тестовом сервере проще всего сделать снимок виртуальной машины. Если снимков нет —
копия всех баз:

```bash
cd /srv/go24
mkdir -p deploy/backups
docker exec go24-postgres-1 pg_dumpall -U postgres | gzip > deploy/backups/before-$(cat VERSION)-$(date +%F).sql.gz
```

Копию базы и файлов можно делать и из самого go24: «Настройки → Резервное копирование → Сделать сейчас».

**2. Новый код.**

```bash
git fetch --tags
git checkout $(git tag --sort=-v:refname | head -1)   # последняя версия; или конкретная: git checkout v0.5.3
cat VERSION
```

**3. Новые настройки.** Покажет параметры, которые появились в новой версии, но которых ещё нет в вашем `deploy/.env`:

```bash
comm -13 <(grep -o '^[A-Z0-9_]*=' deploy/.env | sort) <(grep -o '^[A-Z0-9_]*=' deploy/.env.example | sort)
```

- Пусто — переходите к шагу 4.
- Есть строки — найдите их в `deploy/.env.example` (рядом с каждой есть комментарий) и допишите в `deploy/.env`.
  Если это пароль или секрет и в примере значение пустое, сгенерируйте его командой `openssl rand -hex 32`.

Если в списке изменений версии упомянут мессенджер (Matrix), заново соберите его настройки: `make matrix-config`.

**4. Перезапуск.**

```bash
make up
```

Собирается новый образ go24, при необходимости скачиваются новые версии других сервисов. Обычно это 3–10 минут;
go24 недоступен около минуты в конце.

**5. Проверка.**

```bash
make ps                  # все сервисы running/healthy
make logs s=go24         # нет ошибок при старте (Ctrl+C — выйти)
```

Откройте go24 в браузере и войдите.

## Если после обновления что-то не работает

После обновления по кнопке: **Настройки → Обновление → Откатить** возвращает прежнюю версию вместе с её базой (журнал
обновления — там же и в `make logs s=go24-updater`). После ручного обновления:

1. Посмотрите ошибку: `make logs s=go24` и `make logs s=go24-worker`.
2. Вернуть прежнюю версию кода: `git checkout v<прежняя версия>` и `make up`.
3. Если новая версия уже изменила базу и прежняя с ней не запускается, восстановите снимок виртуальной машины из шага 1.

Восстановление базы из копии `pg_dumpall` вручную — операция тонкая. Если понадобится, лучше спросить разработчиков,
а не делать наугад.
